# 무료 암호화 외부 백업 설계

## 상태

- 설계 방향 승인: 2026-08-01
- 문서 검토 승인: 2026-08-01
- 구현 상태: 미착수

## 1. 목적

Supabase Free를 유지하면서 운영 `jwtennisclub` 데이터베이스를 외부에 복구 가능한
형태로 보관한다. 1단계는 전용 비공개 GitHub 저장소, GitHub Actions, `age` 공개키
암호화를 사용한다. Mac Mini에 접근할 수 있게 되면 2단계로 동일한 암호화 백업을
Google Drive에도 복제한다.

백업은 운영 데이터베이스를 읽기만 한다. 자동 복원은 금지하며, 검증 프로젝트와
운영 프로젝트에 대한 복원은 별도 승인 절차를 거친다.

## 2. 현재 기준선

2026-07-31 읽기 전용 측정 결과는 다음과 같다.

| 항목                         |             크기 |
| ---------------------------- | ---------------: |
| PostgreSQL 전체 데이터베이스 | 13,274,259 bytes |
| `public` 관계                |  1,187,840 bytes |
| 앱·마이그레이션 압축 덤프    |    189,705 bytes |
| Auth·Storage 압축 덤프       |    153,236 bytes |
| Storage 실제 객체            |    0 bytes / 0개 |

메타데이터, 매니페스트, 체크섬과 암호화 오버헤드를 포함한 초기 백업 묶음은 회당
0.5~1MB로 예상한다.

## 3. 비용 경계

이 설계는 다음 무료 할당량 안에서만 동작한다.

- GitHub Free 비공개 저장소
- GitHub-hosted Actions 월 2,000분
- GitHub Actions Artifact 500MB. 장기 백업 저장에는 Artifact를 쓰지 않는다.
- Git LFS 무료 10GB 할당량 안의 암호화 바이너리 저장
- Supabase Free 월 5GB egress와 현재 두 개의 활성 프로젝트
- `age`, PostgreSQL 클라이언트와 검증용 로컬 컨테이너의 무료 도구

GitHub의 사용 예산은 `$0`과 `Stop usage`로 설정한다. 워크플로 작업은 10분 제한,
백업 파일은 초기 10MB 제한을 둔다. 한도나 예상치를 넘으면 과금하지 않고 실패
처리한다. 제공자 가격이나 무료 할당량이 바뀌면 자동으로 유료 기능을 사용하지
않고 운영자가 설계를 다시 승인해야 한다. 현재 일정의 보수적 상한은 Actions 월
400분, Supabase egress 월 100MB다.

## 4. 저장소와 신뢰 경계

새 전용 비공개 저장소 `divclasssg/jwtennisclub-backups`를 사용한다. 현재 공개
저장소인 `divclasssg/jwtennisclub`과 `divclasssg/jwmatch`에는 백업, DB Secret,
암호화 개인키를 저장하지 않는다.

전용 저장소의 기본 브랜치에는 워크플로와 비민감 매니페스트 형식만 둔다. 암호화
백업은 Git LFS가 추적하는 별도 경로에 저장한다. 외부 Pull Request, fork,
`pull_request_target`은 백업 Secret에 접근할 수 없다. 워크플로는 예약 실행과
소유자의 수동 실행만 허용한다.

개인 GitHub Free의 비공개 저장소에는 브랜치 보호가 포함되지 않는다. 유료 기능을
전제로 하지 않고 소유자 한 명, 협업자 0명, 서명된 백업 코드 릴리스 태그, 실행 전
승인된 백업 코드 커밋 SHA 일치 검사를 사용한다. 승인 SHA 변경은 별도 검토와
명시적 저장소 변수 변경을 요구한다.

## 5. 실행 일정

모든 업무 시간은 `Asia/Seoul`로 계산하고, GitHub cron의 UTC 값은 워크플로
내부에서 다시 검증한다.

- 매일 00:30: DB 상태 지문만 계산한다. 직전 성공 백업과 달라졌을 때만 전체
  백업을 만든다.
- 매월 첫째·셋째·다섯째 토요일 전날 23:00: 경기 전 강제 백업
- 해당 경기 다음 날 일요일 00:00: 경기 후 강제 백업
- 매월 1일 01:00: 월간 장기보관 강제 백업
- DB 배포 직전: 수동 강제 백업
- 필요 시: GitHub Actions의 `Run workflow` 버튼으로 수동 강제 백업

수동 실행은 비어 있지 않은 사유를 필수 입력으로 받으며 실행자, 시각, 사유와
결과를 기록한다. 경기 전후 및 수동 백업은 내용이 같더라도 별도 감사 시점으로
보존한다.

GitHub 예약 실행은 정확한 시각을 보장하지 않으므로 일반 변경의 목표 RPO는
24시간이다. 경기 전후 강제 백업은 경기 데이터의 손실 구간을 줄이지만 PITR처럼 두
백업 사이의 임의 시각을 복원하지는 못한다.

## 6. 변경 감지

변경 감지는 개인정보 원문을 출력하거나 보관하지 않는다. 승인된 앱, Auth, Storage
메타데이터 테이블의 결정적 행 해시와 함수·정책·마이그레이션 정의 해시를 합성해
상태 지문을 만든다. 로그인 시각처럼 Auth에서 바뀐 값도 복구 대상 변경으로
취급한다.

테이블 또는 스키마가 허용목록에 새로 생기면 조용히 제외하지 않고 백업을 실패시켜
범위 검토를 요구한다. 상태 지문 계산이 실패해도 변경 없음으로 간주하지 않는다.

## 7. 백업 범위와 형식

백업 묶음은 다음을 포함한다.

- 승인된 사용자 정의 역할과 권한
- `public`, `match` 스키마의 구조, RLS, 함수, 트리거와 데이터
- `supabase_migrations` 이력
- Auth 사용자·identity와 복구에 필요한 관리형 테이블 데이터
- Storage bucket·object 메타데이터
- 활성 확장과 복원에 필요한 비민감 프로젝트 설정 목록
- 프로젝트 ref, PostgreSQL 버전, 생성 시각, 테이블별 행 수·해시
- 각 구성 파일의 SHA-256을 담은 내부 매니페스트

Supabase 관리형 Auth·Storage 스키마 구조는 새 프로젝트가 제공하는 기준선을
사용하고, 검증된 데이터 허용목록만 복원한다. API 키, SMTP 비밀번호, OAuth client
secret 등 플랫폼이 내보내지 않는 Secret은 백업에 넣지 않으며 복구 시 새로
발급하거나 별도 Secret 저장소에서 복원한다.

Storage 실제 객체는 현재 0개다. 객체 수가 0보다 커졌는데 2단계 객체 백업이 아직
준비되지 않았다면 백업 완전성 경고 이슈를 만들고 전체 복구 가능 상태라고
표시하지 않는다.

## 8. 암호화와 Secret

`age` 공개키 암호화를 사용한다.

- GitHub에는 암호화 공개키인 recipient만 저장한다.
- 복호화 개인키는 GitHub, Supabase, 백업 저장소와 Actions Secret에 두지 않는다.
- 개인키는 암호화된 이동식 저장장치와 신뢰할 수 있는 비밀번호 관리자 등 서로
  독립된 두 곳에 보관한다.
- DB 연결 정보는 개별 GitHub Secret으로 보관하고 로그와 명령 인자에 포함하지
  않는다.
- libpq 환경과 검증된 TLS CA, `sslmode=verify-full`을 사용한다.
- 평문 덤프는 권한이 제한된 임시 디렉터리에서만 존재하며 작업 종료 시 GitHub
  임시 실행기와 함께 폐기된다.

개인키 분실은 복구 불능이고 개인키 유출은 기존 백업 노출이므로, 최초 백업을 운영
가능으로 선언하기 전에 두 사본과 실제 복호화 시험을 확인한다.

## 9. 생성·검증 흐름

1. 운영 프로젝트 ref와 TLS 대상이 승인값인지 검증한다.
2. 읽기 전용으로 현재 상태 지문을 계산한다.
3. 변경 감지 실행이면 이전 지문과 비교하고, 강제 실행이면 비교를 건너뛴다.
4. 역할, 스키마, 데이터와 메타데이터 묶음을 생성한다.
5. 덤프 목록과 내부 매니페스트를 검증한다.
6. 임시 Supabase/PostgreSQL 환경에 복원한다.
7. 원본과 복원본의 허용목록, 행 수와 내용 해시를 비교한다.
8. 검증 성공 묶음만 `age`로 암호화한다.
9. 암호문 SHA-256과 비민감 외부 매니페스트를 생성한다.
10. 전용 비공개 저장소에 저장하고 업로드 결과를 재확인한다.

어느 단계든 실패하면 새 백업을 성공으로 기록하지 않는다. 동시 실행은 한 개로
제한하고, 중복 실행은 대기시키지 않고 최신 강제 실행을 우선한다.

## 10. 보존정책

- 변경 기반 일간 백업: 최근 14개
- 경기 전후 백업: 최근 12개
- 월간 백업: 최근 12개
- 수동 및 배포 직전 백업: 자동 삭제 제외

Git 이력과 LFS 사용량은 월별로 측정한다. 무료 한도의 70%에서 경고하고 80%에서
신규 장기보관본 생성을 중단하되, 상태 확인과 실패 알림은 유지한다. 백업 삭제는
암호화 파일, 포인터와 매니페스트를 함께 검증한 뒤 수행한다. Git 참조에서
삭제해도 원격 LFS 사용량이 즉시 회수된다고 가정하지 않는다. 80%에 도달하면 새
비용을 승인하지 않고 2단계 저장소 이전 또는 이력 정리 절차를 별도로 검토한다.
수동 백업도 파일·사용량 상한을 우회할 수 없다.

## 11. 실패 감지

- 실패한 Actions 실행은 기본 GitHub 알림을 발생시킨다.
- 전용 비공개 저장소에 하나의 백업 상태 이슈를 열거나 갱신한다.
- 마지막 성공 상태 확인이 36시간보다 오래되면 stale 경고를 기록한다.
- 마지막 성공 백업이 오래됐더라도 상태 지문이 동일했다는 증거가 없으면 정상으로
  간주하지 않는다.
- DB 인증, TLS, 허용목록 변경, 파일 크기, 복원 해시 불일치는 모두 fail-closed
  처리한다.

## 12. 복구와 훈련

- 최초 설정 시 개인키로 실제 복호화와 로컬 복원을 수행한다.
- 변경된 백업은 암호화 전에 임시 환경 복원을 통과해야 한다.
- 매월 개인키 복호화 시험을 수행한다.
- 분기마다 기존 검증 프로젝트에 전체 복원 훈련을 수행한다.
- 검증 프로젝트 복원은 별도 승인 후에만 실행한다.
- 운영 복원은 현재 운영 DB의 사전 백업과 명시적 사용자 승인 없이는 실행하지
  않는다.

복구 순서는 역할, 스키마, 마이그레이션 이력, 앱 데이터, Auth 데이터, Storage
메타데이터다. 복원 후 회원·경기 체크섬, Auth 집계, RLS·함수와 Storage
메타데이터를 비교한다. 현재 규모의 목표 RTO는 60분이며 최초 훈련의 실측치로
확정한다.

## 13. 2단계 이중화

Mac Mini 승인 접근이 가능해지면 다음을 추가한다.

- `launchd`로 백업 저장소의 새 암호문 동기화
- 제한된 `drive.file` 권한의 rclone Google Drive remote
- 기존 암호문을 복호화하지 않은 채 Google Drive에 복제
- Drive 업로드 체크섬과 보존정책 검증
- Mac 로컬에는 장기 평문을 남기지 않음

2단계는 1단계의 백업 형식이나 개인키를 바꾸지 않는다.

## 14. Task 8 복구 게이트 변경

현재 Task 8 검증기는 물리 백업과 PITR 활성화, RPO 15분 이하만 허용한다. 무료
백업을 성공시켰다는 이유로 이 증거를 가장하거나 기존 필드를 `true`로 채우지
않는다.

검증기는 다음 두 복구 프로필 중 정확히 하나를 받도록 버전업한다.

- `managed-pitr-v1`: 기존 물리 백업, PITR, RPO 15분과 복원 증거
- `logical-offsite-v1`: 이 문서의 암호화 외부 백업, 목표 RPO 24시간, 임시 환경
  복원 해시, 개인키 복호화 시험과 검증 프로젝트 복원 증거

무료 프로필은 최신 성공 상태 확인이 36시간 이내이고, 변경 발생 후 다음 예약
실행에서 새 백업이 생성됐으며, 마지막 분기 복원 훈련이 유효할 때만 통과한다.
경기 전후 강제 백업 누락과 Storage 객체 미보호 상태는 별도 실패 조건이다. 릴리스
증거에는 선택한 프로필과 실제 RPO를 기록해 PITR과 동등하다고 표시하지 않는다.

이 게이트 변경은 구현 계획과 코드 리뷰를 거쳐야 하며, 실제 복원 검증이 완료되기
전에는 Task 8 릴리스를 허용하지 않는다.

## 15. 수용 기준

- 운영 DB에 쓰기 없이 최초 전체 백업 성공
- 공개 저장소와 로그에 Secret 또는 평문 데이터가 없음
- 임시 환경 복원 및 원본/복원본 해시 일치
- 실제 개인키 복호화 성공과 두 개의 독립된 키 사본 확인
- 예약·변경 감지·경기 전후·수동 실행 테스트 성공
- 실패 이슈와 stale 감지 테스트 성공
- GitHub와 Supabase 무료 사용량 예상치 기록
- GitHub `$0` 예산과 초과 사용 중단 확인
- 검증 프로젝트 복원 성공 전에는 기존 Task 8 복구 게이트를 통과한 것으로
  표시하지 않음

## 16. 제외 범위

- Supabase PITR 또는 물리 백업과 동일한 보장 주장
- 운영 DB 자동 복원
- 공개 저장소에 백업 저장
- 앱 관리자 화면에서 백업 실행
- 운영 DB 트리거로 외부 백업 호출
- 현재 단계의 Google Drive 자동 업로드
